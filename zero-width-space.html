What a zero-width space is

U+200B ZERO WIDTH SPACE is a real character that takes up no room. It exists so a browser knows where it may break a long word. It is invisible, it survives copy and paste, and it is the single most common reason a string that looks identical to another one fails to match it.

It is not the only one. The characters below are all invisible and all survive a copy:

  • U+200B zero width space
  • U+2060 word joiner
  • U+FEFF zero width no-break space, better known as a BOM
  • U+00AD soft hyphen
  • U+034F combining grapheme joiner
  • U+E0001 language tag and U+E0020–U+E007F tag characters
  • Private use characters: U+E000–U+F8FF, plane 15, plane 16

How to spot one

The symptoms are more recognizable than the character:

  • Two strings that render identically compare as unequal
  • A database lookup or a grep misses a line you can see
  • JSON or YAML fails to parse with a confusing error near an ordinary character
  • A backspace seems to do nothing once
  • Code copied from a page or a chat refuses to compile

Paste the text above and this page marks each one where it sits, then removes it.

Your font decides whether it stays invisible

Nothing about U+200B makes it invisible. It is invisible because the font that ends up serving it has a glyph for it that advances zero and paints nothing. Change which font serves it and the answer can change — and on a page loading a web font, that choice is made before the character is drawn at all, by one line of CSS.

A subsetted web font declares which code points it is willing to serve with unicode-range. Four pages were rendered in the same browser with the same real font file behind them, differing only in that one declaration:

A thousand invisible characters and not one byte of the font; a single invisible character inside the declared range and the whole file comes down. The range is matched on the code point alone. It does not ask whether the character has a visible glyph, and it does not ask how many of them the page is carrying.

Leaving it out breaks nothing. Developer tools report which family actually drew each run of text, and in the first two rows above that family is the second name in the stack, not the web font. The character arrives intact either way — it is simply being served by a font the page never chose for it.

That is worth knowing because the obvious way to check gives the wrong answer. document.fonts.check("40px Face", "\u200B") returns true whether U+200B is inside the range or outside it: across the four rows above it was true for a character no face had been asked to cover, and false for one that had, at the moment the file was still arriving. The method reports the load state of the faces that match. A character no face matches needs nothing loaded, so it passes.

What the family in your CSS is actually worth

On the machine these numbers come from the agreement is absolute. Twenty-two families named one at a time, at sizes from 8 px to 96 px: U+200B advanced 0.00 px and painted nothing in every one of them. In twenty-one of the twenty-two the family reported as having drawn it was the family that was named; the exception was a Japanese family that is not installed here, where the browser substituted a different one without saying so.

Substitution is the ordinary case for other members of the same set. Ask any of those twenty-two families for U+3164, the Hangul filler, and all twenty-two are answered by the same Korean font, which gives it a full em — 64 px at 64 px, 16 px at 16 px — while painting nothing. Ask for U+070F and all twenty-two are answered by a historic-script font, whatever you named. The family in your stylesheet is a request, not a guarantee.

When nothing on the device has the code point at all, what gets drawn is the font’s own replacement glyph, and that is not a standard shape either. Measured at 64 px against a code point no font defines:

It runs from half an em to a full em, and in one family here it reserves a whole character cell and paints nothing at all — a gap the width of a character with no mark in it. A device whose fonts differ from the ones measured here can substitute a drawn glyph for a character that is invisible on this one, and the character itself never changed.

Measured in this tab on a canvas at 64 px: how far the caret moves, and how many pixels get painted. The last row is the control — a code point no font defines, so what it shows is that family’s replacement glyph. Which family really drew each one is something the browser only reports to developer tools.

If you ship a subsetted font, the decision is worth making on purpose rather than inheriting. Left out, U+200B costs nothing to render and is handed to whatever family comes next, which for a zero-advance character changes nothing you can see. Included, every page that carries one downloads a file for a glyph that is never painted. And none of this touches the copy: the character rides along in the clipboard whichever family drew it.

Which removal recipe actually removes it

Line up the fifteen invisible characters a piece of text is most likely to be carrying and run the usual cleanup snippets over them one at a time: they do not remove the same set. The most widely copied JavaScript recipe for this job takes four of the fifteen, and two of those four are the characters holding Persian words and emoji families together.

Two of the eleven survivors are worth knowing by name. The word joiner U+2060 is the character most blank-text tools hand out, because unlike U+200B it never offers the browser a place to break a line — and it walks straight through the four-character recipe, whose range stops at U+200D. The combining grapheme joiner U+034F survives even \p{C}, because Unicode files it under Mn, a combining mark, and not under C at all: the property that reads as “every invisible character” is not that property.

The damage from the four-character recipe is not visible in the result. Run it over a family emoji — one grapheme, seven code points — and you get four code points back: the three joiners are gone and what was one picture is now four separate people in a row. The same eight-code-point Persian word comes back as seven, the same five-code-point Devanagari word as four. Both still render. Neither is the string you started with.

The shell has the same split, only there it is silent. sed 's/\u200B//g' matches nothing and exits 0; so does sed 's/\x{200b}//g'. The forms that work are the one written in bytes, sed 's/\xe2\x80\x8b//g', and a literal character handed over by the shell, tr -d $'\u200B'. A cleanup pass built on the escape form reports success and changes nothing.

One disagreement sits between two languages usually assumed to agree. JavaScript’s trim() deletes U+FEFF and Python’s strip() does not; the pattern \s matches U+FEFF in JavaScript and not in Python. Both agree on U+00A0, U+2028, U+2029 and U+202F. So a field holding five U+FEFF characters is empty to a browser and five characters long to the Python script that reads it.

That is the line the two modes above are drawing. Default takes out the eight characters that are never load-bearing — U+00AD, U+034F, U+200B, U+2060, U+FEFF and the three interlinear annotation characters — including the two that both popular recipes leave behind. Aggressive adds the joiners, the direction marks and the bidi isolates, and the warning under it is there because that is the point where cleanup starts changing what the text says. What this keeps by default

Some invisible characters carry meaning, so they stay unless you turn on aggressive mode:

  • U+200D zero width joiner — holds emoji families together
  • U+200C zero width non-joiner — needed for Persian, Arabic and Devanagari
  • U+FE0F variation selector 16 — keeps emoji rendering as emoji
  • Regional indicator pairs (flags) and bidi marks in matched pairs
